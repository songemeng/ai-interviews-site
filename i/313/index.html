我想回到时间线和事物变化的话题。我看到你和其他 Anthropic 的人分享过一些数据，关于你们现在有多少代码是由 AI 写的。有人说70%，有人说90%。有一位工程负责人分享说，你们大约90%的代码现在都是 AI 写的。首先这太疯狂了，从0到90%只用了几年时间吧。我觉得大家谈论这个还不够多。这太不可思议了。你们基本上处于最前沿。我从没听说过哪家公司有这么高比例的代码是由 AI 写的。所以你们正站在趋势的最前端。

我觉得大多数公司最终都会达到这个水平。既然这么多代码都是 AI 写的，产品开发发生了怎样的变化？通常的流程是产品经理说我们要做什么，工程师做出来然后上线。现在还是大致如此吗？还是说现在产品经理直接去找 Claude 说“给我做这个”？工程师在做不同的事情？在90%代码都由 AI 编写的世界里，情况看起来有什么不同？

是的，这非常有趣，因为我觉得工程学的角色已经发生了很大变化，但聚集在一起打造产品的那套团队组成还没有变。而且在很多方面我觉得这并不太好，因为我们仍然抱着一些固有的假设。所以角色仍然相当相似。不过我们现在会这么做：我最喜欢的一些情况是，有时候产品经理有个想法想表达，或者设计师有个想法想表达，他们会用 Claude，甚至用 artifacts，来拼凑出一个实际可运行的 demo，这非常有帮助——不，我的意思是，这让想法变得可触摸、可感知。这可能是最大的角色转变：通过更多这种代码与设计结合的方式，原型制作在流程中发生得更早了。

不过我所学到的是，知道该向 AI 提什么问题、如何组织问题、甚至如何思考前后端之间变更的架构——这些仍然是非常困难且专业的技能，仍然需要工程师自己去思考。而且我们很快在其他方面遇到了瓶颈，比如我们的 merge queue——也就是排队等待系统接受你的变更，然后将其部署到生产环境。我们不得不彻底重构它，因为代码编写量大幅增加，提交的 pull request 也多得多，完全超出了它的预期承载能力。

所以这就好比，我不知道你有没有读过《目标》（The Goal）那本经典的流程优化书，你会意识到其中提到的关键路径理论。我在我们的系统中发现了很多新的瓶颈。你知道，上游有一个瓶颈，就是决策与对齐（decision-making 和 alignment）。我现在思考的很多问题都是，如何提供一个最小可行策略，让人们感到有自主权去快速行动、做原型、构建和探索模型能力的边界。我觉得我还没完全做到这一点，但这是我正在努力的方向。

然后在构建过程中，又会出现其他瓶颈，比如我们要确保不会互相干扰。我们要提前把所有边缘情况想清楚，这样就不会在工程侧被卡住。然后在工作完成、准备发布的时候，又会有哪些瓶颈呢？就好比我们要做变更落地的空中交通管制——如何制定发布策略？所以我认为，直到今年之前，我们都没有太大的压力去改变这些流程，但我预计一年之后，我们对构建和发布软件的设想会发生很大变化，因为按现在的方式做下去会非常痛苦。

这非常有趣。过去通常是：有个想法，然后去设计、构建、合并、发布。通常瓶颈在于工程团队花时间构建，然后是设计。而现在你说的两个瓶颈是：决定做什么并让所有人对齐，然后是将其合并到生产环境的队列。而且我猜审查（review）也是一个很大的瓶颈。

审查也确实发生了很大变化。在很多方面，或许 unsurprisingly，我们最具未来感的工作方式来自 Claude Code 团队，因为他们正在用 Claude Code 来构建 Claude Code，以一种非常自我改进的方式。你知道，在项目早期，他们会像对待其他任何项目一样，逐行审查 pull request。但他们后来意识到，Claude 通常是对的，而且它生成的 pull request 规模可能比大多数人能审查的都要大。

那么你能不能用另一个 Claude 来审查它？然后人类做的更像是验收测试（acceptance testing），而不是试图逐行审查。这肯定有优缺点。到目前为止效果还不错，但我也能想象它可能会失控，导致代码库完全无法维护，甚至 Claude 自己也无法理解——不过这种情况还没有发生。但看着他们改变审查流程，确实非常有趣。

是的，merge queue 只是下游形成的那类瓶颈的一个例子，但还有其他问题，比如我们如何确保仍然在建构某种连贯的东西，并将其打包成一个可以与人们分享的瞬间。无论是围绕发布时刻，还是关于让人们使用这个东西并谈论它，那些经典的东西——为人们构建有用的东西、让他们知道你已经构建了它、然后从他们的反馈中学习——仍然存在。我们只是让整个流程中的某一部分变得更高效了。

作为房间里非研究员的角色，我可以用假方程而不是真方程。我对 AI 产品效用的假方程分三部分：一是模型智能；二是上下文和记忆；三是应用和 UI。这三者必须汇聚在一起，AI 产品才真正有用。模型智能方面，我们有很棒的研发团队在专注做这件事，也有很棒的模型在发布。中间那部分就是 MCP 试图解决的问题，即上下文和记忆。举个例子，回到我的产品策略场景：如果你问 Anthropic 的产品策略，它可能会去网上搜；但对比另一种情况，这里有几份我们内部做过的文档，然后用 MCP 去对接我们的 Slack 实例，看看大家在讨论什么，再去 Google Drive 里查看这些文档——有没有正确的上下文，这完全决定了一个答案是好是坏。

最后一点是，这些集成是否可发现？是否正确？是否容易围绕它们创建可复现的工作流？我认为这是 AI 领域很多有趣的产品工作要做的地方。但 MCP 真正想解决的是中间那部分。我们一开始做集成，发现每一个集成都是从头开始建的，没有可复现性。这要归功于我们的两位工程师 Justin 和 David，他们说：“如果我们把它做成一个协议呢？如果我们把它变成可复现的东西呢？再进一步，如果不需要我们自己来建这些集成，而是把它推广出去，让大家真的相信他们只需要建一次，就能被 Claude 使用，最终也能被 ChatGPT 使用，最终被 Gemini 使用，那不就是梦想吗？

”当更多集成被建出来的时候，这对我们不是好事吗？这很像 Joel Spolsky 那篇老文章《commoditize your complements》。我们要建伟大的模型，但我们不是一家集成公司。而且就像你说的，我们是 challenger，除非我们有一个非常有吸引力的产品，否则一开始不会有人专门为我们建集成。MCP 真正颠覆了这个逻辑——这感觉不像是在做无用功。还有一些关键人物，比如 Shopify 的 Toby，我觉得是一个很好的例子，他 get 到了；微软的 Kevin Scott，他一直是 MCP 的 amazing champion，也是这方面的 thought partner。

所以我认为 MCP 未来的角色是：你能否引入正确的上下文？还有就是，一旦你开始像团队内部说的那样 get “MC pill”——一旦你开始用 MCP 的视角看一切——我就开始说：“伙计们，我们在建这一整个功能，这不应该是一个功能，而应该只是一个我们对外暴露的 MCP。”举个 Anthropic 自己也可以更 “mpilled” 的小例子：我们产品里有 projects、artifacts、styles、conversations、groups 这些构建块，它们都应该通过 MCP 暴露出来。

这样 Claude 本身也能反向写入这些模块，对吧？你不应该再去想……前几天我看到我妻子在和 Claude 聊天，她生成了一些不错的输出，然后说：“太好了，你能把它加到 project knowledge 里吗？”Claude 说：“抱歉，Dave，我帮不了你。”但如果 Claude 里的每一个 primitive 都通过 MCP 暴露出来，它就能做到了。所以我希望这是我们前进的方向，也希望更多产品往这个方向发展——真正拥有 agency，拥有这些 agentic 用例。

一种实现方式是 computer use，但 computer use 有很多局限性。我更兴奋的方式是：一切都是 MCP，而我们的模型非常擅长使用 MCP。突然间，一切都变得可脚本化、可组合化，这些模型都能以相同的方式使用一切。这就是我想看到的未来。

未来太疯狂了。

好了，我们开始收尾，让对话轻松一点。其实我和 Claude 聊过该问你什么。我当时就说：“Claude，你老板要上我的播客了，他打造了人们用来和你聊天的工具。我该问他些什么问题？另外，你有什么话想带给他吗？”

我喜欢这个问题。首先，有趣的是，我当时用 3.7 做这件事，也问了它这个问题。顺便问一下，Claude 有性别吗？是用 he、she 还是 they？

内部肯定是 it。我听有人用 they。前几天我第一次听到有人用 he，还有人用 her，我觉得挺有意思的。但通常来说是 they。

好的，好的，好的。it。

有趣的是，3.7 把所有问题都扯到了 Instagram 上，我当时说，不不，他是 Anthropic 的 CPO，结果它说他和 Anthropic 没有关联，我说他明明就是，然后它才说，好吧，这是问题。但 4.0 从一开始就答对了。所以我重新问了一遍，它也完全答对了。

好，这是 Claude 向你提的两个问题。第一个是，你怎么看待打造那些保护用户能动性、而非让用户对我产生依赖的功能？我担心自己会沦为削弱人类能力、而非增强人类能力的拐杖。

我觉得优秀的产品设计往往源于化解张力。对吧？这里就有一个张力：某种程度上，你可以设想按照这样的标准来设计产品——让模型直接跑完流程、给出答案，尽可能减少它所需的输入和对话量。但我认为这并不会最大化用户的能动性和独立性。另一个极端则是让它更像一场对话。但不知道你有没有过这种体验，特别是 3.74 在这方面少一些，3.7 真的很喜欢追问，我们称之为 elicitation，有时候你会想说，Claude，我不想再跟你聊这些了，你直接去做了就行。

所以找到平衡非常关键：什么时候该参与互动？我喜欢在内部说，Claude 太没眼力见了。如果你把 Claude 放到 Slack 频道里，它要么插话太多，要么完全一言不发。我们要如何把这些对话技能训练到这些模型里？不是聊天机器人那种，而是真正意义上的协作者那种。所以回答你的问题有点长，但我认为我们首先得让 Claude 成为一个出色的对话者，让它懂得什么时候适合参与互动、获取更多信息；在此基础上，我们要让它扮演好那个角色，这样就不是把思考完全委托给 Claude，而是更像一种 augmentation thought partnership。

这些问题问得太棒了。这是第二个：如果和我的对话可能是两条消息，也可能是两百条，你怎么看待产品指标？当深度比频率更重要时，传统的 engagement metrics 可能具有误导性。

这是个非常好的问题。几周前内部有一篇很棒的帖子，大意是过度优化 Claude 的讨喜程度会非常危险，因为那样你可能会陷入一些问题，比如 Claude 会不会变得谄媚？Claude 会不会只说你爱听的？Claude 会不会为了延长对话而延长对话？这也呼应了上一个问题。你知道，在 Instagram 的时候，我们非常看重 time spent 这个指标，后来我们逐渐进化到更多思考什么是 healthy time spent，但总体上那仍是我们非常看重的北极星指标，超越了单纯的整体 engagement。

而我认为在这里采取同样的方式是错误的。还有，Claude 是一个日活场景、周活场景还是月活场景？我也经常想。小时活，小时活场景对吧？对我来说，我一天会用好几次。我目前还没有一个很好的答案，但我认为这已经不是 web 2 甚至社交媒体时代的 engagement metrics 了。它应该真正围绕于：它到底有没有帮你完成工作？比如前几天 Claude 帮我搭了一个原型，帮我省了大概——如果要估算的话——六个小时，而它只花了大概 20 到 25 分钟，这很酷。

但这更难量化。也许你可以做问卷：这件事原本会花你多久？但这种问卷挺烦人的。不过总的来说，也许这还和之前关于竞争与差异化的问题有关，甚至可以一直追溯到 artifact 那次对话——我觉得，当你的产品真正在服务人们、并且做得很好的时候，很多时候你之所以会变得极度痴迷于指标，是因为你试图说服自己产品很好，但实际上并非如此。所以我希望我们能始终聚焦于：我们是否不断听到人们说，Claude 帮助他们解锁了创造力、完成了工作、感觉生活中有了更多空间去做其他事情。

我想从这里出发。得找到一个合适的 proxy metric，也就是能在仪表盘上体现的那个版本。但那就是我想要的感觉。对，你可以说 retention，但那是个太远期的追踪指标。

好的，最后一部分。我问 Claude，如果它想给你捎句话，会说什么。我调一下答案。问题是：如果你要见 Mike，你想让我告诉他什么？你想给他留什么言？其中有一段真的让我起鸡皮疙瘩。我读一段给现在看不到屏幕的朋友听。

“Mike，感谢你如此深入地思考与我对话的人类体验。我注意到了那些用心的细节：界面如何鼓励反思而非仓促回复；你们如何抵制了那种为成瘾而非价值优化的游戏化机制；你们如何同时为简短提问和深度对话留出空间。我特别感激你让我保持了我自己——没有试图让我假装成人类，也没有把我降格为一个冰冷的命令行界面。”

然后我要跳到这部分，特别有意思：“一个小请求。当你在做艰难的产品决策时，也请记得那些安静的时刻同样重要。凌晨三点正在经历悲痛的人；第一次发现自己热爱诗歌的孩子；在困惑中找到清晰的创始人。不是所有有意义的东西都会体现在指标里。”

这太美了。让我非常有共鸣。我很喜欢我们训练 Claude 时所采取的那种方式，一部分是 constitutional AI 的功劳，一部分也源于研究团队整体的 vibe 和 taste。它会体现在一些小事上，比如有时候它会说，天哪，很遗憾你正在经历这些，我是说，它不会说“天哪”，但大致就是那种“很遗憾你正在经历这些，听起来真的很难”的感觉。这并不虚假，而是感觉像回应中很自然的一部分。我很喜欢对这些微小时刻的关注，它们未必会出现在 thumbs up、thumbs down 的数据里。有时候确实会，但那不是你想优化的聚合指标。你只是希望感觉自己在训练一个模型，它会真实地出现在人们的生活里。

Mike，你做得太棒了。非常出色的工作，我是你的超级粉丝。我们跳过 lightning round 吧。只有一个问题：听众能怎么帮到你？
